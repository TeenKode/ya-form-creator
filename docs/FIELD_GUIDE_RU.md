# Как ИИ должен выбирать поля анкеты

Формат конфигурации и тип API — разные вещи. У нас `text` превращается в API `string`; `format` выбирает штатный валидатор. Не пишите `type: "email"`, `type: "phone"`, `type: "fio"` или `type: "number"`.

## Таблица соответствия

| Что просит пользователь | Конфигурация YaFormCreator | Что важно |
| --- | --- | --- |
| ФИО одним полем | `type: "text", format: "full_name", multiline: false` | Не заставлять вводить три слова или отчество. Поддерживать дефисы, апострофы, разные языки. |
| Имя, фамилия, отчество раздельно | Три отдельных однострочных `text` с `format: "full_name"` | Разделять только по заданию. Отчество не делать обязательным автоматически. |
| Российский телефон | `text`, `format: "phone"`, `multiline: false` | Значение — строка. Нативный валидатор Яндекса ориентирован на РФ. |
| Международный телефон | Однострочный `text` без format либо `format: "plain"` | Не навязывать российский формат; согласовать страны и ограничения. |
| Электронная почта | `text`, `format: "email"`, `multiline: false` | Не заменять обычным текстом без проверки, если запрошена почта. |
| Адрес сайта / ссылка | `text`, `format: "url"`, `multiline: false` | В предпросмотре ожидается полная HTTP/HTTPS-ссылка; Яндекс проверяет окончательно. |
| ИНН | `text`, `format: "inn"`, `multiline: false` | Не целое число: сохранять строковое представление, в том числе ведущие нули. |
| Возраст / количество / целое значение | `integer` | `min`/`max` — только по заданию, не угадывать возрастные границы. |
| Вес / стоимость / дробное значение | `text`, `format: "decimal"`, `multiline: false` | `min_length`/`max_length` ограничивают символы, а не величину числа. Числовые границы для decimal пока не поддержаны. |
| Номер заказа / заявки / договора | Однострочный `text` | Коды `000123`, `АБ-0042` не должны становиться 123 или 42. |
| Номер паспорта / серия / СНИЛС | Однострочный `text` | Маску/длину/контрольную сумму задавать только при явном требовании и поддерживаемой схеме. Встроенного format snils/passport нет. |
| Почтовый индекс | Однострочный `text` | Фиксировать длину только при известной стране и явном требовании. Не терять ноль в начале. |
| Банковский счёт / БИК / артикул | Однострочный `text` | Идентификатор, а не арифметическое число. Не обещать проверку по внешним реестрам. |
| Полный адрес | `text`, при необходимости `multiline: true` | Не подменять ссылкой. Не делить на город/улицу/дом без задания. |
| Дата рождения / события | `date` | Границы `YYYY-MM-DD` задавать только если требуются. Не подставлять сегодняшнюю дату как ответ. |
| Подтверждение «да / нет» | `boolean` | Это выбор из двух ответов. Если требуется только утвердительное согласие, required у boolean недостаточно: нужно уточнить нужную логику. |
| Один из вариантов | `radio` или `dropdown` | `options` минимум из двух точных подписей. |
| Несколько вариантов | `checkbox` | Не использовать radio; min/max_choices — по заданию. |
| Произвольное дополнительное поле | Подходящий поддерживаемый тип | Неизвестный тип не заменять молча «похожим». Уточнить назначение; API payload — только при известной схеме. |

### ФИО не имеет универсальной регулярки

`full_name` — понятное назначение однострочного текстового поля, **без отдельного серверного валидатора имени**. Принимаются, например, одно имя, двойная фамилия или имя с апострофом. Это не проверка личности и не поиск в справочнике сотрудников. Корпоративное поле «Люди» — другой API-тип и другая задача.

### Неоднозначное слово «номер»

«Добавь номер» недостаточно для выбора integer. Уточните: телефон, номер документа, заказа или числовое количество? Не переделывайте «номер квартиры» в телефон. Если текст прямо говорит «номер заказа», храните его текстом; дополнительный вопрос не нужен.

### Три разных значения слова «уникальный»

1. **Уникальный код поля:** каждый `slug` уникален внутри анкеты, включая автоматически созданные поля `other.slug`.
2. **Специальное поле:** телефон, ФИО и почта требуют разного назначения и иногда валидации формата.
3. **Неповторяющийся ответ среди респондентов:** нельзя реализовать добавлением `unique: true`. В приложении нет базы ответов и проверки дублей ФИО/телефонов. `allow_multiple_answers: false` также не гарантирует уникальность телефона. Объясните ограничение и уточните отдельную серверную интеграцию; не обещайте реализованную защиту от дублей.

## Поддерживаемые свойства текстового вопроса

`type`, `slug`, `label`, `required`, `comment`, `placeholder`, `hidden`, `multiline`, `min_length`, `max_length`, `format`.

`format`: `plain`, `full_name`, `phone`, `email`, `url`, `inn`, `decimal`. Если format специальный, multiline должен быть false или отсутствовать (движок выберет false). Для обычного текста без multiline историческое значение по умолчанию — true; агенту лучше всегда задавать его явно.

Не пишите верхнеуровневые `validators`, `validation`, `regex`, `pattern`, `unique`: движок отклонит их вместо молчаливой потери ограничения. Для точно известного нестандартного API-объекта есть `type: "api"` с валидаторами **внутри payload**. Локальный предпросмотр не проверяет произвольные API-валидаторы.

Ограничение длины и формат независимы. `required: false` разрешает оставить поле пустым; если ответ введён, его формат проверяется. `placeholder` — подсказка, не ответ и не проверка. Не записывайте реальные ФИО, телефоны, документы или другие ответы в конфигурацию.

## Пример отдельного поля (не готовая анкета)

```json
{"type":"text","slug":"contact_email","label":"Электронная почта","format":"email","multiline":false,"required":true}
```

## Проверка перед выдачей

- Сверьте каждый вопрос с исходным заданием, включая порядок и обязательность.
- Убедитесь, что у телефонов и кодов не используется integer/decimal и не подставлены initial/default с ответами.
- Проверьте полное имя без выдуманных ограничений; формат телефона должен соответствовать нужной стране.
- Условия используют точные подписи вариантов и предшествующие вопросы. Для обычных текстовых полей этот конструктор не поддерживает источники условий.
- Выполните offline-check и dry-run, откройте предпросмотр. Проверки подтверждают программный контракт, а не понимание произвольным ИИ всех пожеланий.

## Источники и пределы проверок

Проверено по документации Яндекса 6 ноября 2026 года: [валидация ответов](https://yandex.ru/support/forms/ru/option-validation) и [создание вопроса API](https://yandex.ru/support/forms/ru/api-ref/questions/events_b2b_v1_views_questions_create_question_public_view). В API email, phone, url, inn и decimal — валидаторы `string`, а не самостоятельные типы вопросов.

Предпросмотр выполняет предварительную проверку: базовый синтаксис email, телефон РФ, HTTP/HTTPS-ссылка, длина и контрольные цифры ИНН, десятичная запись. Алгоритмы и допустимые значения Яндекса могут отличаться; окончательно проверьте черновик. Успешная проверка формата не подтверждает существование почты, принадлежность телефона или регистрацию ИНН.
